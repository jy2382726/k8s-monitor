## 1. 容量与规模基线

### 1.1 实际节点数与 master taint

#### 1.1.1 文档假设（来自 06 §1.1）

| 指标 | 文档假设值 | 实际环境值（待填） |
|---|---|---|
| master 节点数 | 3 | ___ |
| worker 节点数 | 25 | ___ |
| 节点总数 | 28 | ___ |
| master 是否有 taint | 假设有（默认 NoSchedule）| 是 / 否 |
| worker 是否有自定义 taint | 假设无 | 是 / 否 |

#### 1.1.2 关键概念

- **节点数 = `kubectl get nodes` 的数量**
- **Taint** = 节点上的"拒客标签"，Pod 默认不能调度
- **Toleration** = Pod 声明"我能忍受这个污点"

#### 1.1.3 为什么需要对齐

1. **影响 DaemonSet 副本数**：`node-exporter` 每节点 1 个 Pod（含 master，需容忍 taint）
2. **影响 PVC 数量**：Prometheus 2 副本 × 100Gi + Alertmanager 3 副本 × 5Gi + Grafana 10Gi
3. **影响 HA 决策**：Alertmanager 3 副本必须能打散到 3 个不同 worker
4. **影响调度策略**：master 有 taint 时，监控组件（除 node-exporter）应调度到 worker

#### 1.1.4 核对命令

```bash
# 节点总数
kubectl get nodes --no-headers | wc -l

# 按角色分类（推荐方式）
kubectl get nodes -l node-role.kubernetes.io/control-plane --no-headers | wc -l
kubectl get nodes -l node-role.kubernetes.io/worker --no-headers 2>/dev/null | wc -l

# 备用方式（worker 没有 role label 时）
kubectl get nodes --no-headers | grep -v master | wc -l

# 查所有 taint
kubectl get nodes -o json | jq '.items[] | {name: .metadata.name, taints: .spec.taints}'

# 简化版
kubectl describe nodes | grep -A 3 Taints
```

#### 1.1.5 风险场景（针对 25 worker 场景）

| 场景 | 风险 | 对策 |
|---|---|---|
| 实际 worker < 3 | Alertmanager 3 副本 quorum 无法打散 | 减副本为 2（接受偶发双发风险）或加 master toleration |
| master 有 taint、worker 有专用 taint | 监控组件 Pending | 必须给监控组件加完整 toleration |
| 节点数和文档差超过 ±5 | 时间序列估算要重新算 | 重新跑 §1.2 核对 |

### 1.2 活跃时间序列实测

#### 1.2.1 概念澄清

**活跃时间序列（Active Time Series）** = 集群中**所有 scrape job 在最近一个时间窗口内有过数据点**的、不重复的"指标名+label 组合"总数。

#### 1.2.2 与"采集次数"的关系

```
样本数/天 ≈ 活跃序列数 × (86400 / scrape_interval)
示例：100k 活跃序列 × 30s 间隔 = 100k × 2880 = 2.88 亿 sample/天
```

#### 1.2.3 文档估算的拆解（06 §1.1）

| 来源 | 估算量级 |
|---|---|
| node-exporter（28 节点 × ~1000） | ~28,000 |
| kubelet cadvisor（容器 × 50-200） | ~10,000-80,000 |
| kube-state-metrics（Pod × 15-25） | ~3,000-10,000 |
| 集群级对象（Deployment/Service/Node 等） | ~2,000-5,000 |
| 应用自定义指标（一期不接入） | 0 |
| 自监控（Prometheus / Alertmanager） | ~2,000-5,000 |
| **合计** | **~50k-150k** |

#### 1.2.4 怎么核对（按优先级排序）

**方法 A：集群已有 Prometheus（最准）**
```promql
count(prometheus_tsdb_head_series{name!=""})
```

**方法 B：临时起一个采样 Prometheus 跑 1 小时**
```bash
# 用最小化 Prometheus + node-exporter + kube-state-metrics
# 跑 1 小时后查 head_series
```

**方法 C：纯经验估算**
```bash
# node-exporter 单节点指标数
curl -s http://<node-ip>:9100/metrics | grep -v '^#' | awk '{print $1}' | sort -u | wc -l

# Pod/容器规模
kubectl get pods -A --no-headers | wc -l
```

#### 1.2.5 与资源配置的关系（06 §3.2 已修订）

| 活跃 series | 06 文档配额 | 是否需要调整 |
|---|---|---|
| 50k | Prometheus 2 CPU / 8Gi 内存 | ✅ 充裕 |
| 100k | Prometheus 2 CPU / 8Gi 内存 | ✅ 合理 |
| 200k | Prometheus 2 CPU / 8Gi 内存 | ⚠️ 边界，观察 |
| 500k+ | Prometheus 2 CPU / 8Gi 内存 | ❌ 需调高到 12-16Gi |

**经验公式**：每百万 series 约 6-8 GiB 内存（含 head + chunk cache + 查询开销）。

**06 文档已给 8GiB 内存配额**，对应 50k-200k 合理。如果实测 > 200k，需：
- 调高 memory limit 到 12-16Gi
- 或裁剪 kube-state-metrics allowlist
- 或降低 scrape 频率

## 2. HA 与调度约束

### 2.1 Alertmanager 3 副本 quorum（**06 决策 3**）

#### 2.1.1 为什么必须 3 副本（不是 2）

**2 副本的致命缺陷**：网络分区时无法形成 quorum，两个副本都继续发送通知 → **重复告警**。

**3 副本的正确性**：
```
网络分区场景（A | B C）：
- A 是 1/3，自我隔离，不发送
- B C 是 2/3，形成 quorum，B 或 C 发送
- 结果：唯一通知 ✅
```

#### 2.1.2 关键配置（来自 06 §3.2 + §3.8）

```yaml
alertmanager:
  alertmanagerSpec:
    replicas: 3  # ⚠️ quorum HA，不是 2 副本
    podAntiAffinity: requiredDuringSchedulingIgnoredDuringExecution
    topologySpreadConstraints:
      - maxSkew: 1
        whenUnsatisfiable: DoNotSchedule
        topologyKey: kubernetes.io/hostname
        labelSelector:
          matchLabels:
            app.kubernetes.io/name: alertmanager
    resources:
      requests: {cpu: 100m, memory: 256Mi}
      limits: {cpu: 500m, memory: 512Mi}
    storage:
      volumeClaimTemplate:
        spec:
          storageClassName: ssd
          resources:
            requests:
              storage: 5Gi
    retention: 120h
    cluster:
      listenAddress: "0.0.0.0:9094"  # Gossip 端口
    podDisruptionBudget:
      minAvailable: 2  # 维护期至少 2 副本可用
```

#### 2.1.3 "节点分散"的核心问题

| 情况 | 风险 | 后果 |
|---|---|---|
| ≥ 3 worker 节点 + 反亲和 | ✅ 正常 | HA quorum 有效 |
| 2 worker 节点 + 3 副本 | ❌ 1 个 Pending | quorum 失效 |
| 1 worker 节点 + 3 副本 | ❌ 2 个 Pending | 完全失效 |

**判断标准**（针对 25 worker 场景）：
- 25 worker >> 3 副本 → **绝对安全**
- 无需担心打散问题

#### 2.1.4 核对命令（部署后）

```bash
# 看副本分布（期望 3 个 Pod 在 3 个不同节点）
kubectl get pods -n monitoring -l app.kubernetes.io/name=alertmanager -o wide
# 期望 NODE 列三行不同

# 看 Gossip 集群状态
kubectl logs -n monitoring alertmanager-0 --tail=50 | grep -i cluster
# 期望看到 "cluster peers: 3"

# 看 PDB
kubectl get pdb -n monitoring -l app.kubernetes.io/name=alertmanager
```

### 2.2 Prometheus 2 副本 HA（**06 决策 2**）

#### 2.2.1 工作模式

Prometheus 2 副本是**独立采集 + Alertmanager 去重**模式：
- 2 副本都 scrape 所有 target
- 2 副本都评估规则
- 2 副本都发送告警到 Alertmanager
- Alertmanager 通过 Gossip 去重，确保告警只发一次

#### 2.2.2 关键配置

```yaml
prometheus:
  prometheusSpec:
    replicas: 2
    retention: 30d
    retentionSize: 85GiB  # 绝对值
    resources:
      requests: {cpu: 2, memory: 8Gi}
      limits: {cpu: 4, memory: 12Gi}
    storageSpec:
      volumeClaimTemplate:
        spec:
          storageClassName: ssd
          resources:
            requests:
              storage: 100Gi
    # ⚠️ 禁用 lifecycle API（06 §3.2 安全要求）
    enableAdminAPI: false
    # 不启用 --web.enable-lifecycle（默认禁用）
    # 告警发送到所有 Alertmanager
    alertingEndpoints:
      - name: alertmanager-operated
        namespace: monitoring
        port: 9093
        pathPrefix: /
        apiVersion: v2
    # 规则评估由 Prometheus 完成（不是 Grafana）
    ruleSelector:
      matchLabels:
        release: kps
```

#### 2.2.3 核对命令

```bash
# 副本分布（期望 2 个 Pod 在 2 个不同节点）
kubectl get pods -n monitoring -l app.kubernetes.io/name=prometheus -o wide

# 检查 lifecycle API 是否禁用
kubectl exec -n monitoring prometheus-0 -- \
  wget -qO- http://localhost:9090/-/healthy 2>&1 | head
# 期望返回 "Prometheus is Healthy"

# 试图访问 reload API（应该失败）
kubectl exec -n monitoring prometheus-0 -- \
  wget -qO- --post-data="" http://localhost:9090/-/reload 2>&1 | head
# 期望返回 403 或 connection refused
```

### 2.3 监控组件调度到 worker 节点（**06 §7**）

#### 2.3.1 调度目标

```
Prometheus-0      ──→  worker-01
Prometheus-1      ──→  worker-02
Alertmanager-0    ──→  worker-03
Alertmanager-1    ──→  worker-04
Alertmanager-2    ──→  worker-05
Grafana           ──→  worker-06
kube-state-metrics-0  ──→  worker-07
kube-state-metrics-1  ──→  worker-08
blackbox-exporter ──→  worker-09
node-exporter     ──→  所有节点（含 master）★ 例外
```

`node-exporter` 是 DaemonSet，**必须**采 master 指标，所以它要容忍所有 taint。

#### 2.3.2 核对 master 和 worker 的 taint 现状

```bash
# 1. master taint
kubectl get nodes -l node-role.kubernetes.io/control-plane \
  -o json | jq '.items[].spec.taints'
# 典型输出：
# [{"key":"node-role.kubernetes.io/control-plane","effect":"NoSchedule"}]

# 2. worker taint（如果有）
kubectl get nodes -l node-role.kubernetes.io/worker \
  -o json | jq '.items[].spec.taints'
# 如果是 [] 或 null 表示无自定义 taint

# 3. worker 标签（关键：nodeSelector 需要）
kubectl get nodes -l node-role.kubernetes.io/worker --show-labels
```

⚠️ **如果 worker 节点没有 `node-role.kubernetes.io/worker` label**（默认 K8s 不会自动打），
部署前必须手动添加：

```bash
# 给所有 worker 节点打 label
for node in $(kubectl get nodes -l '!node-role.kubernetes.io/control-plane' -o name); do
  kubectl label $node node-role.kubernetes.io/worker=
done
```

#### 2.3.3 部署策略 A：worker 无自定义 taint（推荐）

```yaml
prometheus:
  prometheusSpec:
    nodeSelector:
      node-role.kubernetes.io/worker: ""
    # 只容忍 master taint（让 K8s 调度器知道我们不去 master）
    # 实际上 nodeSelector 已足够，不需要 toleration
```

#### 2.3.4 部署策略 B：worker 有自定义 taint

```yaml
prometheus:
  prometheusSpec:
    nodeSelector:
      node-role.kubernetes.io/worker: ""
    tolerations:
      # 按实际 taint 配置，不要凭空假设
      - key: "<actual-taint-key>"  # 替换为实际值
        operator: "Equal"
        value: "<actual-taint-value>"
        effect: "NoSchedule"
```

#### 2.3.5 `kube-prometheus-stack` 推荐 values（worker 无自定义 taint）

```yaml
prometheus:
  prometheusSpec:
    nodeSelector:
      node-role.kubernetes.io/worker: ""
    affinity:
      podAntiAffinity:
        requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchLabels:
                app.kubernetes.io/name: prometheus
            topologyKey: kubernetes.io/hostname

alertmanager:
  alertmanagerSpec:
    nodeSelector:
      node-role.kubernetes.io/worker: ""
    podAntiAffinity: requiredDuringSchedulingIgnoredDuringExecution
    topologySpreadConstraints:
      - maxSkew: 1
        whenUnsatisfiable: DoNotSchedule
        topologyKey: kubernetes.io/hostname
        labelSelector:
          matchLabels:
            app.kubernetes.io/name: alertmanager

grafana:
  nodeSelector:
    node-role.kubernetes.io/worker: ""

kube-state-metrics:
  nodeSelector:
    node-role.kubernetes.io/worker: ""

prometheus-node-exporter:
  # ⚠️ node-exporter 要容忍所有 taint（包括 master）
  tolerations:
    - operator: Exists  # 容忍所有 taint
```

### 10.3 与文档假设的偏差处理

| 偏差类型 | 处理方式 |
|---|---|
| 节点数与文档差 > ±5 | 重新计算 PVC 和内存 |
| worker 节点数 < 3 | Alertmanager 减副本为 2（接受风险）或加 master toleration |
| worker 无 `node-role.kubernetes.io/worker` label | 部署前手动 `kubectl label node` 添加 |
| master 有 taint 且 worker 有专用 taint | 加完整 toleration（按实际 taint 配置）|
| 活跃序列 > 200k | 调高 Prometheus 内存到 12-16Gi |
| 没有 ssd storage class | 用 default 或新创建（避免 NFS）|
| 已有 ArgoCD | 复用，不重复部署 |
| 已有 Flux | 06 决策 ArgoCD，迁移到 ArgoCD 或保留 Flux 做其他用途 |
| 无 ingress | 改 NodePort（不推荐）或部署 ingress-nginx |
| 无 VPN | 这是硬约束，必须先解决 |
