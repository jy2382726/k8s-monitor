## 4. 推荐组合对比

### 4.1 方案 A：最小化自研（“拼成熟组件”）

**目标**：最快上线、最低研发风险，适合已有运维团队能接受多组件部署和配置维护的场景。[双路 ✅]

**推荐组件组合**：

| 层级 | 组件 |
|---|---|
| 部署基线 | `prometheus-operator/kube-prometheus` |
| 指标采集 | `prometheus/prometheus` + `prometheus/node_exporter` + `kubernetes/kube-state-metrics` |
| 告警路由 | `prometheus/alertmanager` |
| 通知 | `feiyu563/PrometheusAlert` 或 `timonwong/prometheus-webhook-dingtalk`（只需钉钉时） |
| 存储 | 先用 Prometheus 本地 TSDB；如需长期存储接 `VictoriaMetrics` 或 `Thanos` |
| 可视化 | `grafana/grafana` |
| 多集群 | `thanos-io/thanos`（当 1-3 集群必须全局查询时） |
| 日志可选 | `grafana/loki` |

**为什么推荐**：

1. `kube-prometheus` 已经把 Prometheus Operator、Prometheus、Alertmanager、node-exporter、blackbox-exporter、Prometheus Adapter、kube-state-metrics、Grafana 打包为 K8s 监控基线，可最大化减少自研部署和规则工作。[双路 ✅]
2. Prometheus + Alertmanager + Grafana 是行业事实标准，社区规模大，Star 数分别为 64,394、8,499、74,311，生态风险低。[双路 ✅]
3. 对中型集群，直接套用 kube-prometheus 的规则和 Dashboard 可以快速形成可用监控面板与告警规则。[双路 ✅]
4. 国内通知需求可用 PrometheusAlert 或 webhook-dingtalk 补齐，不必自研钉钉/飞书/短信/电话渠道。[双路 ✅]

**为什么不用 X / 使用限制**：

- 不把 `Grafana` fork 成自己的前端：其 AGPL-3.0 对商业闭源分发有合规影响，且图表生态无需重复造轮子。[双路 ✅]
- 不一开始上 `Thanos`：对于 1-3 个中型集群，如果没有强长期存储、对象存储和全局查询诉求，Thanos 组件复杂度偏高。[双路 ✅]
- 不直接 fork `Prometheus`：Prometheus README 明确其主仓库构建独立程序，不设计为稳定 Go library；直接部署比 fork 更稳。[路A]
- `timonwong/prometheus-webhook-dingtalk` 只适合钉钉单渠道，若需要飞书、企微、短信、电话，应优先用 PrometheusAlert 或 Nightingale。[双路 ✅]

**适用场景**：

- 项目优先级是快速上线、稳定运维、少写代码。[双路 ✅]
- 接受多组件配置和后续升级维护。[双路 ✅]
- 当前只需要 1-3 集群的指标监控、告警与可视化，不强调统一产品化 UI。[双路 ✅]

**主要风险**：

- 组件较多，用户体验分散在 Grafana、Alertmanager、PrometheusAlert / Nightingale 等多个页面。[双路 ✅]
- 若用 kube-prometheus 的 Jsonnet 自定义，学习与升级成本不低。[路A]
- 若引入 Grafana / Loki，需注意 AGPL-3.0 合规边界。[双路 ✅]

### 4.2 方案 B：适度自研（“核心开源 + 自研运维门户”）

**目标**：保留成熟开源底座，适度自研统一运维入口、告警策略模板、集群资源视图、通知配置与业务化体验。[双路 ✅]

**推荐组件组合**：

| 层级 | 推荐实现 |
|---|---|
| 指标底座 | `prometheus/prometheus` + `node_exporter` + `kube-state-metrics` |
| 存储 | `VictoriaMetrics/VictoriaMetrics`（中型集群优先） |
| 告警底座 | Prometheus rules + `prometheus/alertmanager` |
| 通知聚合 | 参考 / 集成 `feiyu563/PrometheusAlert` 的渠道适配与模板机制 |
| 告警管理模型 | 参考 `ccfos/nightingale` 的业务组、规则、静默、订阅、pipeline、历史告警统计 |
| 可视化 | Grafana 直接嵌入或链接；自研只做轻量概览面板 |
| 多集群 | 暂用 VictoriaMetrics 全局写入 / 查询；强多集群 HA 时再引入 Thanos |
| 日志 | Loki 作为二期可选模块 |

**建议自研的部分**：

1. **统一运维门户**：集群列表、节点健康、命名空间/工作负载概览、告警概览、最近异常事件。[双路 ✅]
2. **规则模板管理**：把 kube-prometheus / kubernetes-mixin 中常用规则做成可启停、可参数化模板。[双路 ✅]
3. **通知配置抽象**：参考 PrometheusAlert 的多渠道通知实现，但封装为本项目统一配置模型。[双路 ✅]
4. **告警生命周期页面**：参考 Nightingale 的业务组、告警历史、静默、订阅、pipeline 思路。[双路 ✅]
5. **Grafana 嵌入 / 跳转**：不自研复杂 Dashboard，只提供关键链接和预置 Dashboard 管理。[双路 ✅]

**为什么推荐**：

- 对 10-100 节点、1-3 集群，中型规模更关注“可用 + 易用 + 通知闭环”，而不是从零打造指标引擎。[双路 ✅]
- VictoriaMetrics 的单节点/集群方案能降低长期存储和高基数指标成本，复杂度通常低于 Thanos 全套编排。[双路 ✅]
- Nightingale 与 PrometheusAlert 都显示国内告警运营场景的设计价值，但直接 fork 可能带来技术栈、UI、权限、产品边界不一致的问题；因此更适合参考模型或拆模块复用。[双路 ✅]

**为什么不用 X / 使用限制**：

- 不用 Nightingale 完全替代本项目：Nightingale README 明确自身不做数据采集，且高级 on-call / 排班升级不是其强项；本项目仍需集成采集、存储、集群视图。[路A]
- 不用 PrometheusAlert 作为整个系统主体：它强在通知聚合和模板，弱在现代 K8s 监控门户、可视化、业务权限和多集群产品体验。[双路 ✅]
- 不把 Loki 放入 MVP：Loki 是日志系统，能增强排障，但指标监控告警 MVP 不依赖日志聚合；另外 AGPL-3.0 需合规评估。[双路 ✅]
- 不强行引入 Thanos：中型 1-3 集群先用 VictoriaMetrics 更简单；除非明确需要 Prometheus HA 对象存储长期保存和全局查询。[双路 ✅]

**适用场景**：

- 希望产品体验统一，而不是多个开源页面拼起来。[双路 ✅]
- 团队有一定研发资源，可以做门户、规则模板、通知配置、告警生命周期管理。[双路 ✅]
- 需要兼顾国内通知渠道与 K8s 运维语义。[双路 ✅]

**主要风险**：

- 自研门户会引入持续维护成本；必须严格限制边界，不要重写 Prometheus / Grafana / Alertmanager 的核心能力。[双路 ✅]
- 需要设计好 License 合规：Apache-2.0 / MIT 组件复用较宽松；Grafana / Loki 的 AGPL-3.0 只能直接部署使用或按许可证履约。[双路 ✅]

## 5. 结论

### 推荐优先级

1. **MVP 推荐走方案 A 的基础栈**：`kube-prometheus` + Prometheus + Alertmanager + node_exporter + kube-state-metrics + Grafana，再按通知需求接 PrometheusAlert 或 webhook-dingtalk。[双路 ✅]
2. **产品化版本推荐走方案 B**：指标与存储底座用 Prometheus / VictoriaMetrics，告警底座用 Alertmanager，通知适配参考 PrometheusAlert，告警管理模型参考 Nightingale，自研统一门户。[双路 ✅]
3. **多集群长期存储**：如果只是 1-3 个中型集群，优先 VictoriaMetrics；只有明确需要 Prometheus HA + 对象存储长期保留 + 全局 Query 时再上 Thanos。[双路 ✅]
4. **可视化不自研**：Grafana 直接集成或嵌入，避免重复造图表平台；注意 AGPL-3.0 合规。[双路 ✅]
5. **日志作为二期能力**：Loki 可用于告警排查联动，但不是指标监控告警 MVP 的核心依赖。[双路 ✅]

### 最终建议架构

- **采集层**：node_exporter + kube-state-metrics + Prometheus scrape。[双路 ✅]
- **存储层**：Prometheus 本地短期 + VictoriaMetrics 长期存储（中型集群优先）。[双路 ✅]
- **规则与告警层**：Prometheus rules + Alertmanager；规则模板参考 kube-prometheus。[双路 ✅]
- **通知层**：多渠道用 PrometheusAlert / 参考其设计；仅钉钉可用 prometheus-webhook-dingtalk。[双路 ✅]
- **可视化层**：Grafana + 预置 Dashboard。[双路 ✅]
- **告警运营层**：参考 Nightingale 的业务组、静默、订阅、pipeline、历史告警统计，自研轻量门户。[双路 ✅]
- **多集群层**：先用 VictoriaMetrics 简化；必要时引入 Thanos。[双路 ✅]
