# 集群开关机操作手册

> 适用场景：下班关机 / 长期不用 / 要把内存还给 Windows / **不关机只停 K8s 腾资源做别的项目**
> 对应集群：`k8s-monitor-dev`（kind，3 节点）
> 当前进度（2026-07-08）：**Phase 5 全部完成 + Phase 6 echo/Ingress 验证通过**（6 组件 + echo-server 全 Running，三域名经 Ingress 可达）。下次继续 **Phase 6 Task 6.3 baseline + Phase 7 运维资产**。

## 0. 必读：为什么需要这份手册

停服务 ≠ 删集群，**数据不会丢**。但要理解两个关键事实：

| 容器 | restart policy | 关机/重启 WSL 后的行为 |
|---|---|---|
| `k8s-monitor-dev-control-plane` / `worker` / `worker2` | **`on-failure`** | ❌ **不会自动起**，必须手动 `docker start` |
| `kind-registry` | `always` | ✅ Docker 一起来就自动起 |

- 集群所有数据（etcd、Pod 状态、已部署组件）存在节点容器的可写层——**只要不 `docker rm` 节点容器、不 `kind delete cluster`，怎么停数据都在**。
- 节点起来后，kubelet 会自动把 metrics-server / ingress-nginx / cert-manager / kube-prometheus-stack / ArgoCD 等 Deployment 重新拉起，**无需重装任何组件**。

> ⚠️ **两个绝对禁止**：`kind delete cluster` 和 `docker rm <节点>`，这俩会删掉 etcd，集群直接报废，得从 Task 5.1 重建。

> 📌 **本手册两种「停」**：
> - **关电脑（下班）**→ 用 [第一节](#一关机前停服务约-30-秒)（`wsl --shutdown`，连 WSL 一起关）
> - **不关电脑、只腾资源做别的**→ 用 [第二节](#二不关机只停-k8s-集群腾资源做别的项目)（`docker stop` 节点，WSL 保留）

## 一、关机前：停服务（约 30 秒）

在 **Windows PowerShell**（任意终端）执行：

```powershell
wsl --shutdown
```

- 优雅关闭整个 WSL2 虚拟机（Docker、kind 节点、registry 全部停止）
- 等约 8 秒后正常关机即可
- **为什么先 `wsl --shutdown` 再关机**：让 WSL2 收到优雅关闭信号，避免直接断电可能导致的文件系统/etcd 轻微不一致。直接关机通常也没事，但先 shutdown 更稳。

## 二、不关机只停 K8s 集群（腾资源做别的项目）

> 场景：WSL 还要用（跑别的项目），但 K8s 集群占着 ~6 GB+ 内存/CPU 要释放。
> 效果：3 个节点容器一停，集群里所有 Pod 冻结、控制面停 → 内存基本全释放；数据保留，一条命令随时恢复。

### 停（释放资源）

```bash
docker stop k8s-monitor-dev-control-plane k8s-monitor-dev-worker k8s-monitor-dev-worker2
```

- 节点是 `on-failure` 策略，stop 后**保持停止、不会自动重启**（即便 Docker daemon 重启也不会被拉起）。
- `kind-registry`（`always`）要不要也停？
  - **只停 3 个节点通常就够了**（registry 占用可忽略，几十 MB 量级）。
  - 想彻底干净：再 `docker stop kind-registry`（但 daemon 一重启它会被自动拉起，因为 `always`）。
- ⚠️ **别停 Docker daemon**（`sudo systemctl stop docker`）——你要干的别的项目如果也用 Docker（别的容器 / 镜像构建），停 daemon 会一起断。**只停 kind 节点 = 精准释放 K8s 占用，不影响其他 Docker 用途**。

验证已停 + 内存归还：
```bash
docker ps --filter "name=k8s-monitor-dev"     # 预期: 空列表（3 节点已停）
free -h                                        # 预期: 可用内存回升（autoMemoryReclaim 几秒~几十秒内归还给 Windows）
```

> 💡 停了节点后 `kubectl get nodes` 会连不上（apiserver 在 control-plane 容器里，已停）——这是正常的，不是集群坏了。

### 恢复（别的项目干完，把集群拉回来）

和「三、开机后」的 **Step 3** 是同一条命令：

```bash
docker start k8s-monitor-dev-control-plane k8s-monitor-dev-worker k8s-monitor-dev-worker2 \
  && echo "节点已启动，等待 Ready..." \
  && kubectl wait --for=condition=ready node --all --timeout=120s \
  && kubectl get nodes \
  && kubectl get pods -A | grep -vE 'kube-system|local-path'
```

看到 3 节点 `Ready`、组件 Pod `Running`，恢复完成。

## 三、开机后：起服务（约 1–2 分钟）

### Step 1：开机进 Windows，打开 WSL 终端

- 正常开机登录
- 打开任一 WSL 终端（Ubuntu / Windows Terminal 的 WSL 标签）
- 这一步会启动 WSL2 虚拟机，systemd 随之启动

### Step 2：等 Docker 自启（systemd 自动，约 10–30 秒）

```bash
systemctl is-active docker        # 预期: active
docker ps --format 'table {{.Names}}\t{{.Status}}'
```

预期看到 `kind-registry` 已自动起来。**3 个 kind 节点此时不在列表里**——正常（`on-failure`，等手动起）。

> 如果 `docker` 还没 active，等几秒再查。开机后第一次进 WSL，systemd 起服务需要点时间。

### Step 3：手动启动 3 个 kind 节点 + 等就绪（一键命令）

复制下面整段执行：

```bash
docker start k8s-monitor-dev-control-plane k8s-monitor-dev-worker k8s-monitor-dev-worker2 \
  && echo "节点已启动，等待 Ready..." \
  && kubectl wait --for=condition=ready node --all --timeout=120s \
  && echo "=== 节点 ===" \
  && kubectl get nodes \
  && echo "=== 组件 Pod ===" \
  && kubectl get pods -A | grep -vE 'kube-system|local-path'
```

预期输出：
```
节点已启动，等待 Ready...
node/k8s-monitor-dev-control-plane condition met
node/k8s-monitor-dev-worker condition met
node/k8s-monitor-dev-worker2 condition met
=== 节点 ===
NAME                            STATUS   ROLES           AGE   VERSION
k8s-monitor-dev-control-plane   Ready    control-plane   ...
k8s-monitor-dev-worker          Ready    <none>          ...
k8s-monitor-dev-worker2         Ready    <none>          ...
=== 组件 Pod ===
NAMESPACE       NAME                               READY   STATUS    RESTARTS   AGE
argocd          argocd-application-controller-0    1/1     Running   ...
argocd          argocd-server-...                  1/1     Running   ...
argocd          argocd-redis-...                   1/1     Running   ...
cert-manager    cert-manager-...                   1/1     Running   ...
e2e-test        echo-...                           1/1     Running   ...
ingress-nginx   ingress-nginx-controller-...       1/1     Running   ...
monitoring      kube-prometheus-stack-grafana-...  3/3     Running   ...
monitoring      prometheus-kube-prometheus-stack-prometheus-0   2/2   Running   ...
（以上为节选，完整约 18 个组件 Pod；RESTARTS 不为 0 属正常——节点重启后 kubelet 重连）
```

看到节点 `Ready`、组件 Pod `Running`，恢复完成。

> 💡 **RESTARTS 列不为 0 是正常的**：节点重启时 Pod 会经历短暂数据重连（如 redis、prometheus），kubelet 自动恢复。**只看 STATUS 是否 Running**，不看 RESTARTS。

## 四、验证清单（可选，确认集群健康）

```bash
# 1. kubectl context 对不对
kubectl config current-context          # 预期: kind-k8s-monitor-dev

# 2. metrics-server 还能用
kubectl top nodes

# 3. ingress-nginx 通（三域名都应 200/302，不再是 404）
curl -sS -o /dev/null -w "echo:      HTTP %{http_code}\n" -H "Host: echo.local" http://localhost/
curl -sS -o /dev/null -w "argocd:    HTTP %{http_code}\n" -H "Host: argocd.local" http://localhost/
curl -sS -o /dev/null -w "grafana:   HTTP %{http_code}\n" -H "Host: grafana.local" http://localhost/
# 预期: echo/argocd = 200，grafana = 302（→/login）

# 4. local registry 通（方案 C 镜像源）
curl -s http://localhost:5001/v2/_catalog | head -c 200
```

> 🌐 **浏览器访问**（Windows hosts + Clash 绕过域都配好的前提下）：
> - `http://echo.local` → echo-server JSON
> - `http://argocd.local` → ArgoCD 登录页
> - `http://grafana.local` → Grafana 登录页（admin / admin123）
> - 浏览器不通但上面 curl 通 → 看 `plan.md` Task 6.2 Step 3 排查清单（多半是 Clash 系统代理 / HTTPS 强升）。

## 五、常见问题

**Q1：开机后 `docker ps` 报 "Cannot connect to the Docker daemon"**
→ Docker 还没起来。`sudo systemctl start docker` 手动起，或再等几十秒。

**Q2：`kubectl get nodes` 一直 NotReady**
→ 节点刚 start，kubelet 还在初始化。等 30–60 秒再查。仍 NotReady 就 `docker restart` 该节点。

**Q3：某些 Pod 一直 `ContainerCreating` / `ImagePullBackOff`**
→ 节点拉镜像要走 local registry，确认 `kind-registry` 在跑（Step 2 应已自动起）。没起就 `docker start kind-registry`。

**Q4：停集群后想彻底删掉重来**
→ 那才是 `kind delete cluster --name k8s-monitor-dev`（**销毁，不是挂机**）。下次要从 Task 5.1 重新建集群。

**Q5：忘了进度到哪**
→ 看 `docs/superpowers/plans/2026-06-25-local-k8s-dev-cluster-plan.md`，或本手册顶部"当前进度"行。当前：**Phase 6 验证完成，待做 Phase 6 Task 6.3 baseline + Phase 7 运维资产**。或问 Claude "集群进度到哪了"。
