# 01-产品形态

> 调研对象：面向中型 K8s 集群（10-100 节点，1-3 集群）的运维监控系统产品形态。
>

> `[双路 ✅]` 表示两路均能支撑；`[单源 ⚠️]` 表示仅一侧或仅单一页面支撑；
> `[冲突 ⚠️ 见下]` 表示第 6 节列出双方来源且不强行裁决。

## 2. 信息架构参考

### 2.1 集群总览页展示哪些关键指标

面向 10-100 节点、1-3 集群，集群总览页应是“健康态势 + 容量风险 + 告警态势 + 最近变化”的一屏入口。[双路 ✅]

推荐模块如下：

1. **全局健康卡片**：集群数、在线/异常集群、节点 Ready 数、NotReady 节点数、命名空间数、工作负载数、当前 firing 告警数、P0/P1 告警数。[路B]
2. **资源容量**：CPU request/limit/usage、Memory request/limit/usage、磁盘/文件系统、网络吞吐、Pod 容量与可调度余量。[路B]
3. **工作负载健康**：Deployment / StatefulSet / DaemonSet 可用副本、Pod Running/Pending/CrashLoopBackOff、重启次数、滚动发布中的工作负载。[路B]
4. **节点视图**：按节点显示 CPU、内存、磁盘、网络、Pod 数、kubelet 状态、节点条件，支持从异常节点下钻到 Pod。[路B]
5. **命名空间/业务维度**：按 namespace、service、team、cluster 标签聚合资源与告警，便于与告警路由标签一致。[双路 ✅]
6. **告警态势**：按 severity、alertname、cluster、namespace、team 展示当前告警分布、近 24h 趋势、Top N 高频告警、被抑制/静默数量。[双路 ✅]
7. **最近事件与变更**：K8s Events、最近部署/扩缩容/节点变更、配置变更与告警时间线并列展示，服务于初步 RCA。[路B]
8. **AI/排障入口**：对 P0/P1 告警给出“影响面、可能原因、建议检查项、相关指标/日志链接”的摘要，而非直接自动修复。[双路 ✅]

设计原则：总览页不要堆满所有图表，而应优先暴露“是否健康、哪里最危险、谁负责、下一步点哪里”。[路B]

### 2.2 告警列表页如何分级、分组展示

告警列表页应以“一个可处理的事件单元”而不是“每条原始 Prometheus alert”为中心。[双路 ✅]

推荐字段与分组：

- **状态**：Firing、Acknowledged、Silenced、Resolved、Suppressed/Inhibited。[双路 ✅]
- **级别**：P0（全局/核心业务不可用）、P1（关键组件或多实例受影响）、P2（单服务/单节点显著风险）、P3（容量/趋势/提示）。[路B]
- **分组键**：`cluster + namespace + workload/service + alertname + severity` 作为默认 fingerprint；节点类告警可用 `cluster + node + alertname`。[路A]
- **聚合展示**：一行展示一个 alert group，显示影响实例数、首发时间、最近更新时间、持续时长、负责人、通知状态、是否已确认/静默。[双路 ✅]
- **排序**：先按 P0/P1、未确认、持续时间、影响实例数排序；已恢复或静默默认折叠。[路B]
- **抑制关系**：当“集群不可达”触发时，子级 Pod/Service 不可达类告警应显示为被 inhibition 抑制，避免大量症状告警刷屏。[路A]
- **下钻**：每个告警组进入详情页，展示触发规则、PromQL、标签、相关指标图、K8s Event、最近变更、通知历史、操作时间线。[双路 ✅]

### 2.3 通知配置页如何配置收件人和渠道

通知配置页应拆成“联系人/团队、渠道、路由策略、模板、升级策略、静默窗口”六类对象。[双路 ✅]

推荐结构：

1. **联系人与团队**：用户、团队、值班组、备份人；团队绑定默认 cluster/namespace/service/team 标签。[路B]
2. **渠道**：钉钉群机器人、Email、Webhook、短信/电话、PagerDuty、Opsgenie、Slack/Teams 等；本项目默认优先钉钉 + Email/Webhook。[双路 ✅]
3. **路由策略**：按 `severity`、`cluster`、`namespace`、`team`、`alertname` 标签匹配到 receiver；Alertmanager 官方也以 routing tree 配置分组、通知时间和 receiver。[路A]
4. **升级策略**：P0 立即通知主值班人，N 分钟未 ACK 升级到备份人/负责人；P1 可延迟短窗口聚合后通知；P2/P3 进入摘要或低频通知。[路B]
5. **模板**：Markdown 默认模板包含标题、级别、对象、持续时间、影响范围、查看详情链接、建议动作；ActionCard 模板用于 P0/P1 增加“查看详情/确认/静默”按钮。[双路 ✅]
6. **维护/静默窗口**：按标签和时间创建 silence，支持发布窗口、例行维护、已知问题，静默要有创建人、原因、到期时间。[路A]

## 3. 告警交互模式

1. **确认（ACK）**：值班人点击确认后，告警组进入 Acknowledged，后续升级通知停止或暂停，表示“有人正在处理”。[路B]
2. **静默（Silence）**：在给定时间内按标签 matcher 抑制通知，适用于维护窗口或已知问题；Alertmanager 官方定义 silence 为“按匹配器在一定时间内 mute alerts”。[路A]
3. **升级（Escalation）**：按升级链先通知一线值班人，等待 N 分钟未 ACK 后通知备份人/负责人，再升级到群/电话/PagerDuty/Opsgenie。[双路 ✅]
4. **分派（Assign / Add participants）**：告警确认后可分派到个人/团队，或给告警组添加参与者，让责任和协作对象清晰可见。[路B]
5. **关闭/恢复（Resolve / Close）**：监控源恢复后告警应转 Resolved；人工关闭只应关闭事件处理状态，不应伪造指标恢复。[路B]
6. **告警归并（Grouping）**：把同类告警合并为单个通知，Alertmanager 官方说明其适合大故障时将数百/数千告警合成一次 compact notification。[路A]
7. **去重（Deduplication）**：同一 fingerprint 的重复触发不反复通知，只更新时间线和计数；Alertmanager 官方明确负责 deduplicating。[路A]
8. **抑制（Inhibition）**：当根因级告警已触发时，抑制症状级告警通知；Alertmanager 官方例子是集群不可达时抑制该集群其他告警。[路A]
9. **告警归属与路由（Routing）**：按 cluster/namespace/service/team/severity 标签路由到不同 receiver，保证“谁拥有谁收到”。[双路 ✅]
10. **时间线与审计**：记录首次触发、通知、ACK、升级、静默、恢复、备注、AI 建议和处理结论，便于复盘。[路B]

| Dynatrace / Datadog / New Relic 横向 | AIOps / Agentic Observability | 路B 将三者归为企业级 AI RCA 较成熟产品，差异在确定性因果、SRE Agent 和 APM 拓扑能力。[路B][单源 ⚠️] | 说明中型集群 MVP 应先做“辅助排障”，不要直接做“自治修复”。[路B] | 路B muyu-search |
| Grafana Cloud | AI 辅助仪表盘、告警调查、根因洞察 | 路A Grafana 官网摘要提到 built-in AI 帮助构建仪表盘、find and fix issues faster；路B 提到 AI triage / root-cause insights。[双路 ✅] | 借鉴“自然语言解释告警 + 推荐查询/看板”的轻量 AI 入口。[双路 ✅] | 路A Grafana 搜索摘要；路B muyu-search |
| Elastic Observability | ML 异常检测、AI Assistant、日志/指标/链路关联 | 路B 结果称 Elastic 适合日志密集场景，具备 ML anomaly detection 和 AI workflows 辅助 RCA。[路B][单源 ⚠️] | 如果后续接日志，可提供“相关日志模式/异常片段”而不是全量日志平台。[路B] | 路B muyu-search |
| 阿里云 ARMS | LLM 告警收敛、故障洞察、影响分析 | 路B 结果称 ARMS 使用 LLM 做告警收敛、fault insight、impact analysis 和 Copilot 探索；路A 官方页确认其云原生 Prometheus/告警能力但未抓到同等 AI 细节。[路B][单源 ⚠️] | 中文运维产品可借鉴“告警收敛 + 影响范围 + 建议动作”的中文摘要能力。[双路 ✅] | 路A 阿里云产品页；路B muyu-search |
| 华为云 AOM | 关联分析、AI 诊断、降噪 | 路B 结果称其用关联分析、横纵向链路和“松鼠 AI”做分钟级故障诊断与降噪；路A 官方页确认 AOM Prometheus 监控覆盖采集、存储、计算、展示、告警。[路B][单源 ⚠️] | 借鉴“指标/日志/链路/事件统一关联”的方向，MVP 先做指标 + K8s Event + 告警历史关联。[双路 ✅] | 路A 华为云 AOM 文档；路B muyu-search |

| Nightingale / AI SRE 生态 | 告警治理 + AI SRE 文章/生态 | 路A Flashcat 博客主题覆盖 AI SRE、告警治理、Nightingale；路B 更强调 Nightingale 自身多源告警和自愈脚本。[双路 ✅] | 借鉴中文告警治理文案、路由配置和自愈脚本入口；AI 能力可作为后续扩展。[双路 ✅] | 路A Flashcat 搜索摘要；路B muyu-search |

AI 化推荐边界：本项目第一版应定位为“AI 辅助排障与告警摘要”，而不是“AI 自动修复系统”。[双路 ✅]

## 5. 通知触达形态与钉钉消息最佳实践

### 5.1 监控产品如何递达运维人员

主流递达链路是：监控规则触发 → 告警归并/去重/抑制 → 按标签路由 receiver → 按级别进入不同通知渠道 → 值班人 ACK/升级/恢复闭环。[双路 ✅]

推荐渠道分层：

- **P0**：钉钉 ActionCard + @值班人/负责人 + 电话/短信或 PagerDuty/Opsgenie 兜底；未 ACK 自动升级。[双路 ✅]
- **P1**：钉钉 Markdown 或 ActionCard + @值班人；短窗口归并后通知，避免同一故障刷屏。[双路 ✅]
- **P2**：钉钉 Markdown 聚合摘要 + 告警中心列表，不强制电话。[路A]
- **P3**：日报/周报、低频摘要、容量趋势提醒，默认不打扰群。[路B]
- **外部协同**：Email、Webhook、PagerDuty、Opsgenie、Slack/Teams、移动端通知可作为不同组织环境下的扩展渠道；Alertmanager 官方 receiver 示例包含 email、PagerDuty、OpsGenie。[路A]

### 5.2 钉钉 Markdown / ActionCard / FeedCard 对比

| 类型 | 官方支持情况 | 适合场景 | 告警产品建议 | 来源标注 |
| --- | --- | --- | --- | --- |
| Markdown | 钉钉官方消息类型表显示接口方式和 Webhook 方式均支持 Markdown；字段包含 `title` 与 Markdown 格式 `text`，并支持 @ 手机号/userId/所有人。[路A] | 告警摘要、影响范围、指标链接、排障建议、同一告警组的多实例列表。[双路 ✅] | **默认使用**，因为结构清晰、实现简单、适合收敛摘要，也符合“监控报警大量消息应整合为摘要”的官方搜索摘要建议。[路A] | 路A：钉钉消息类型官方页 + 自定义机器人接入搜索摘要；路B：钉钉通知结果 |
| ActionCard | 钉钉官方显示 Webhook 支持整体跳转 ActionCard 和独立跳转 ActionCard；`text` 为 markdown，支持单按钮或多按钮。[路A] | P0/P1 告警，需要“查看详情、确认、静默、分派”等强交互入口。[双路 ✅] | **P0/P1 使用**，建议单按钮“查看详情”或双按钮“确认/查看详情”；复杂操作回到系统内完成，避免钉钉卡片按钮过载。[双路 ✅] | 路A：钉钉消息类型官方页；路B：钉钉通知结果 |
| FeedCard | 钉钉官方显示 FeedCard 仅 Webhook 方式支持，接口方式不支持；每项需要 `title`、`messageURL`、`picURL`。[路A] | 资讯流、公告、周报、多链接卡片；路B 认为可用于多项告警归并。[冲突 ⚠️ 见下] | **不作为默认告警形态**，因为缺少确认/静默/分派按钮语义，且强依赖图片字段，容易把紧急告警做成资讯列表。[路A] | 路A：钉钉消息类型官方页；路B：钉钉通知结果 |

### 5.3 为什么默认 Markdown、P0/P1 用 ActionCard、不用 FeedCard

- 默认 Markdown：告警需要表达级别、对象、持续时间、影响范围、触发值、建议动作、详情链接，Markdown 足够表达且 Webhook 支持。[路A]
- P0/P1 用 ActionCard：高优先级告警需要用户立刻进入详情或执行确认/静默，ActionCard 天然支持按钮和跳转。[路A]
- 不用 FeedCard：FeedCard 更像“多条新闻/多链接卡片”，官方字段要求每条有图片 URL，且没有按钮动作；紧急告警更需要明确行动而不是浏览信息流。[路A]
- 兼容策略：P3 容量趋势、日报、周报可以考虑 FeedCard 或 Markdown 摘要，但 P0/P1/P2 默认不使用 FeedCard。[路A]

### 5.4 告警收敛/分组最佳实践

1. **先归并再通知**：按 `cluster + namespace + workload/service + alertname + severity` 生成 fingerprint，同一 fingerprint 在窗口内只发一条主消息。[双路 ✅]
2. **分级通知**：P0 立即发，P1 可 1-2 分钟聚合，P2/P3 进入 5-15 分钟摘要，避免告警风暴。[路B]
3. **症状抑制**：根因级告警如集群不可达、节点不可达触发时，抑制 Pod/Service 级症状告警通知。[路A]
4. **消息更新而非刷屏**：同一告警组新增实例时更新告警中心和摘要计数，钉钉只在级别变化、负责人变化、长时间未 ACK 时再次触达。[路B]
5. **包含行动入口**：每条钉钉消息必须有详情 URL；P0/P1 ActionCard 至少提供“查看详情”，确认/静默可放系统详情页避免误触。[双路 ✅]
6. **维护窗口**：发布/维护前创建 silence，消息中显示“已静默/静默到期时间/创建人/原因”。[路A]
7. **安全与限流**：钉钉自定义机器人要配置安全关键字或签名；大量系统监控报警应整合为摘要，避免群成员被频繁消息打扰。[路A]

## 7. 产品形态推荐

### 7.1 推荐产品形态

本项目推荐做成：**面向中型 K8s 的轻量级“集群总览 + 告警治理 + 钉钉触达 + AI 辅助排障”产品**。[双路 ✅]

推荐边界：

1. **指标优先，不做全量可观测 SaaS**：第一版以 Prometheus-compatible 指标为主，覆盖集群、节点、Pod、工作负载、组件健康和告警规则。[双路 ✅]
2. **告警中心是核心，而不只是看板**：实现 Alertmanager 式 grouping、dedup、routing、silence、inhibition，再补齐 ACK、assign、escalation、timeline 等 On-call 交互。[双路 ✅]
3. **钉钉是默认触达渠道**：默认 Markdown 摘要；P0/P1 使用 ActionCard；FeedCard 仅用于低优先级摘要或周报。[双路 ✅]
4. **AI 做辅助，不做自治**：AI 输出影响范围、可能原因、相关指标/事件、建议检查项、消息摘要；所有确认、静默、升级、恢复由人或明确规则触发。[双路 ✅]
5. **中型集群体验优先**：默认支持 1-3 集群、10-100 节点，信息架构应减少复杂配置，提供预置大盘、预置规则和推荐路由模板。[路B]
6. **可插拔底座**：短期可接 Prometheus/Alertmanager；指标量上升后可接 VictoriaMetrics；日志/链路用 OpenTelemetry/Elastic/Grafana Loki 作为后续扩展。[路B]

### 7.2 推荐 MVP 页面

1. **集群总览**：健康、容量、工作负载、告警态势、最近事件、P0/P1 快速入口。[路B]
2. **告警中心**：告警组列表、分级、确认、静默、分派、升级、恢复、时间线。[双路 ✅]
3. **告警详情 / RCA 辅助**：触发规则、相关指标图、K8s Event、最近变更、AI 摘要、建议动作。[双路 ✅]
4. **通知配置**：联系人、团队、钉钉机器人、路由策略、升级策略、模板、维护窗口。[双路 ✅]
5. **规则与模板**：预置 K8s 规则、阈值规则、PromQL 规则、通知模板、降噪策略。[路B]

### 7.3 为什么不用 X

- **为什么不用纯 Prometheus + Alertmanager UI**：Alertmanager 的 grouping、dedup、routing、silence、inhibition 很适合作为内核，但缺少面向运维团队的 ACK、分派、升级、时间线、钉钉卡片和 AI 摘要体验。[双路 ✅]
- **为什么不用 Datadog / New Relic / Dynatrace 形态全量照搬**：它们适合大型企业全栈可观测和商业 SaaS，本项目目标是 10-100 节点、1-3 集群，若照搬会造成成本、复杂度、数据出境/合规和实施门槛过高。[路B]
- **为什么不用 Elastic Observability 作为第一形态**：Elastic 适合日志检索和多信号关联，但第一版如果先做日志全量平台，会把重点从“集群健康与告警治理”转移到存储和检索成本。[路B]
- **为什么不用 Zabbix 作为主形态**：Zabbix 的主机/网络监控经验值得借鉴，但 K8s 标签、工作负载、namespace、Pod 生命周期和 PromQL 生态更适合 Prometheus-compatible 形态。[路B]
- **为什么不用 Grafana OnCall OSS 作为强依赖**：本轮资料对 OnCall OSS 状态存在时效冲突，长期依赖风险不清；可借鉴其 Alert Group、ACK、silence、escalation 交互。[冲突 ⚠️ 见下]
- **为什么不用 Nightingale 直接替代本项目**：夜莺是强参考，尤其是中文告警治理、多数据源和告警分发；但本项目若要形成自有产品，应保留更聚焦的 K8s 中型集群信息架构和钉钉优先交互。[双路 ✅]
- **为什么不用阿里云 ARMS / 腾讯云 Prometheus / 华为云 AOM 作为默认形态**：云厂商方案降低云上运维成本，但默认绑定云生态；本项目应保持对自建、混合云和多云 K8s 的可迁移性，只借鉴其托管 Prometheus、预置大盘和 AI 故障洞察。[双路 ✅]
- **为什么不用 FeedCard 做默认告警**：FeedCard 更像多链接资讯流，官方格式要求图片 URL 且缺少动作按钮；默认告警更需要 Markdown 的摘要表达和 ActionCard 的行动入口。[冲突 ⚠️ 见下]

### 7.4 最终一句话建议

做一个“Prometheus-compatible 指标底座 + Alertmanager 式降噪内核 + OnCall-lite 告警生命周期 + 钉钉优先触达 + AI 辅助 RCA 摘要”的中型 K8s 运维监控产品。[双路 ✅]
