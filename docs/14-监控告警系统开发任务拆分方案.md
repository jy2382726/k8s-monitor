## 2. 方法论核心：分阶段 + 双轨验收

`writing-plans` skill 的 **Scope Check** 硬规则：「spec 覆盖多个独立子系统时，必须拆成多个 plan，**每个产出可独立测试的软件**」。

M1–M15 是 6+ 个独立子系统（规则 / 收敛 / 触达 / 自监控 / SLO / GitOps）。写成一个巨型 plan 是反模式——第一轮"集群搭建"plan 已达 2918 行，那还只是把集群搭起来；功能层若再堆一个同等量量的 plan，将无法维护、无法增量验收。

**正确切法：按"监控告警链路的可验收段"切，而不是按 M 编号切。**

```
采集(scrape · 已有) → 规则(PrometheusRule) → 收敛(Alertmanager) → 触达(钉钉) → 自监控(Watchdog)
        └─Phase A─┘   └──Phase B──┘     └─Phase C─┘    └─Phase D─┘
```

每个 Phase = 一个独立 plan + 一个可观测的验收门（对应 PRD 的某条 AC）。

**v0.3 新增：双轨验收（agent 预演 + 用户复现）。** 每个阶段不是"agent 跑通就算完"，而是 agent 先真实部署一遍并沉淀**可复现操作手册**，还原环境后由**用户照手册手动复现成功**才算阶段完成。这逼着手册必须真实可复现（经人实测），不能是 agent 自说自话。完整闭环见 §3.3。

### 3.1 关键设计判断（v0.2 修正措辞 + 新增）

1. **alertmanager"两步走"是对 06 §3.2 锁定基线的受控临时偏离，不是无代价的设计判断。**
   06 §3.2 锁定"Alertmanager 必须 3 副本（2 副本网络分区会脑裂双发）"。Phase A 开**单副本**只为缩短早期反馈（快速验证"规则→评估→firing"链路），代价是：该期间无 Gossip / 无 quorum / `AlertmanagerDown` 规则恒真（虽在 Phase D 才上）。**硬约束：Phase B 必须收回到 3 副本 quorum，不得在 A 之后长期停留单副本。** 若不接受临时偏离，备选是 Phase A 直接上 3 副本（接受更慢的早期反馈）。→ 见 §7.2 取舍 1。

2. **北极星指标的"贯通"分两级：Phase C 打通测量链路（单次），Phase F 统计达标。**
   北极星定义是"统计中位 MTTD + 送达率 100%"，需 N 次注入才有样本——这要到 Phase F 全量演练。Phase C 只验证"单次端到端送达 + 测量骨架能记录 T0/T_detect"。Phase C 测 MTTD 时 Watchdog（元护栏）尚未上线（Phase D 才有），故 Phase C 的单次数字仅供参考。

3. **kind 3 节点对 Alertmanager 3×quorum 的限制（OQ-8）——Phase B 的 HA 验收有边界。**
   kind 3 节点强制反亲和 = 每节点恰好 1 个 AM Pod，无冗余；且 3 节点同 Docker 网络，**无法构造有意义的网络分区**。因此 Phase B 的 HA 验收**仅验证拓扑分布合法性 + PDB minAvailable:2 生效 + 停一 Pod 后 quorum 仍成立（2<3）**，**不验证网络分区 / 脑裂**（留生产割接里程碑）。这要在 Phase B plan 里显式声明，避免给团队"已验证 HA"的虚假信心。

4. **M14 拆分为 M14a / M14b，解除 Phase C 对 Phase F 的反向依赖。**
   AC-US1 / AC-US3 要求 ActionCard 含"公网 Runbook 链接"，而原 M14 排在 Phase F，导致 Phase C 验收门反向依赖 F。拆分：**M14a（Runbook 公网托管骨架：托管位置 + URL 字段，内容可 stub）前置到 Phase C**；**M14b（Runbook 真实内容补全 + 值班手册 + 全量演练）留 Phase F**。Phase C 验"链接字段在位"，完整 AC-US1/US3（真实公网 URL）在 F 验。

### 3.3 每阶段双轨验收闭环（v0.3 核心 / v0.6 修订 teardown 机制）

每个 Phase 不是"agent 跑通就算完"，而是走 **6 步闭环**——agent 预演探路 + 用户复现验收，双轨都过才算阶段完成：

```
⓪ 前置凭据就绪    Phase C/D 等含凭据的 Phase，agent 先查所需 Secret 是否就绪（钉钉 webhook+加签 / SMTP 等）；缺则报"凭据未就绪"+创建命令模板，停下不进入预演。建群+注入凭据是维护者人工前置 task，不假装自动化（修复 M3）
① writing-plans   产出 plan（agent 内部执行脚本：纯部署 TDD/RED-first，不含"产手册"task——手册是预演收尾产物，见③）
② agent 预演执行  照 plan 真实部署一遍，跑通"agent 预演验收门"（上表）；预演日志实时落盘（脱敏）；故障注入产物记录待 cleanup
③ 产出操作手册    agent 预演的强制交付物：从②的日志产出手册草稿（独立文件 -草稿.md，不被定稿覆盖）。预演跑通但无草稿 = 预演失败
④ teardown 还原   按资源类型精确还原到"阶段开始态"（三类资源规则 + 故障 cleanup + 资源清单 diff，不只 verify-all）
⑤ 用户复现        用户照定稿手册手动复现一遍（agent 协助/答疑），跑通验收门（长耗时项按降级规则）= 阶段完成
```

**关键约定：**

- **"阶段开始态"** = M1 基座 + 前序所有已验收 Phase 的产物（用户复现版留集群）。teardown **只清本 Phase agent 预演增量**，不动 M1、不动前序 Phase。
- **同一个 kind 集群、串行**：⓪→①→…→⑤ 都在 `k8s-monitor-dev` 上时间串行，非两套环境。用户复现完成后，集群 = 阶段开始态 + 本 Phase（用户版），作为下一 Phase 的"阶段开始态"。
- **每阶段产物**（分文件，互不覆盖，修复 M5）：plan `docs/superpowers/plans/2026-07-09-phase-<X>-<name>.md` + 手册草稿 `docs/phase-manuals/phase-<X>-操作手册-草稿.md` + 手册定稿 `docs/phase-manuals/phase-<X>-<name>-操作手册.md` + 预演日志 `docs/phase-manuals/phase-<X>-预演日志.md`（脱敏）。

**teardown 三类资源规则**（v0.6 修复 H1/H3——`apply→delete` 只对新建型成立，修改型会毁前序 Phase）：

| 资源类型 | 反向操作 | 例 |
|---|---|---|
| 新建型（本 Phase 新建的独立资源） | `kubectl delete` / `helm uninstall` | Phase C 的 webhook-dingtalk Deployment |
| **修改型**（改已有资源 spec，如 AM/PrometheusRule 跨 Phase 改） | **`kubectl apply` 前序态版本 / `helm upgrade -f` 回前序 values**（不是 delete、不是 `helm rollback`——rollback 对同 release 多 Phase 串改不可靠） | AM A 单副本→B 3 副本：teardown = `helm upgrade -f values-phase-A.yaml`；PrometheusRule F 加 T0：teardown = apply Phase A 版规则 |
| 凭据型（Secret/ConfigMap 含敏感值） | **保留不删**（环境凭据非部署产物），跨 Phase 共享，阶段开始态清单追踪 | 钉钉加签 Secret、oncall ConfigMap |

→ 每个 Phase 保留独立 values 片段（`deploy/components/values-phase-<X>.yaml`），修改型 teardown 用它回退。

**故障注入产物清理**（v0.6 修复 H2——verify-all 检"基座健康"检不出故障残留）：
`inject-fault.sh` 每个注入接口配 `cleanup` 子命令（uncordon 节点 / delete 测试 CrashLoop·OOM Pod），teardown 末尾跑 `inject-fault.sh cleanup --all`。

**阶段开始态资源清单 diff**（v0.6 修复 H2——verify-all 不够）：
闭环②预演开始前 `kubectl get prometheusrules,alertmanagerconfigs,deployments,secrets,configmaps -n monitoring -o name > phase-<X>-start-state.txt`；闭环④ teardown 后再跑一次 diff，确认只剩 M1+前序 Phase 资源（凭据型 Secret 允许保留）。有差异 = teardown 不彻底，补全再验。

**长耗时验收降级规则**（v0.6 修复 M1——双轨翻倍成本）：
- Watchdog 1h 心跳（Phase D）：agent 预演练完整周期（≥2h 确认 2 条），用户复现只验"第 1 条心跳 1h 内到达"。
- Phase F MTTD 统计：agent 预演跑全量 N×5 取中位，用户复现每类故障抽验 1 次（链路通 + 单次不爆表）。

**手册修正迭代回路**（v0.6 修复 L2）：
闭环⑤用户复现失败 → (a) 排障/措辞问题：直接改手册，用户从失败步重试，不重跑预演；(b) 步骤/命令问题（部署逻辑变）：修手册 + 重跑闭环②预演确认，再交用户复现。

**手册格式**（参考 `deploy/开关机操作.md` 风格；v0.6 加"前置凭据"段修复 H3）：
```
0. 前置凭据准备：用户复现前需自备的凭据清单（钉钉 webhook+加签 / SMTP 等）+ 获取方式 + 创建 Secret 命令模板（值留 <FILL_ME>）
1. 前置状态：阶段开始态 + 本阶段前置 OQ 已闭环
2. 步骤：每步 = 完整命令 + 预期输出（逐行可对照），可复制粘贴
3. 验收：本阶段验收门断言（inject-fault.sh 注入 + 期望告警）；长耗时项按降级规则标注
4. 排障：agent 预演踩过的坑 + 解法（手册最值钱的部分，不可省略）
5. teardown：按三类资源规则给反向命令 + inject-fault.sh cleanup --all + 资源清单 diff 命令
```

**阶段完成判定**：闭环⑤用户复现跑通验收门（降级后的，对应 AC 的 Given/When/Then 实跑通过）+ 手册末尾附"用户复现记录"（日期 + 通过的 AC + 偏差）。agent 预演（②）跑通**不等于**阶段完成——只是手册可信的前提。

## 4. 技能组合

遵循用户既有偏好：**拒绝 speckit 重状态机，采用 superpowers 轻量组合**（见 auto-memory `feedback-spec-tooling-preference`）。

| 用途 | 技能 | 何时用 |
|---|---|---|
| **切分 6 阶段**（decompose） | `superpowers:brainstorming` | 只用**这一次**，产出"阶段切分 design"存 `docs/superpowers/specs/` |
| **每阶段写 plan** | `superpowers:writing-plans` | 每阶段一次（闭环①），plan 是 agent 执行脚本 |
| **agent 预演执行** | `superpowers:subagent-driven-development`（推荐）或 `superpowers:executing-plans` | 每阶段一次（闭环②），真实部署 + 跑通验收门 |

## 5. IaC 项目的 TDD 适配（v0.2：区分三类验收门）

`writing-plans` 默认 TDD 节奏是 `写失败单测 → 跑红 → 实现 → 跑绿`。**本项目无单元测试框架**，且并非所有验收门都能"先红后绿"。按验收门类型区分：

| 验收门类型 | 能否"先红后绿" | 处理方式 |
|---|---|---|
| **L0 verify-all 检查**（存活 / Pod Ready / APIService Available） | ✅ 可 RED | 先写检查项（必 FAIL）→ 实现 → 跑 PASS。沿用铁律"第一个 task 写 RED，最后 task 跑绿"。 |
| **L1 行为契约 AC**（如 AC-US2 收敛、AC-US4 停副本被发现） | ⚠️ 部分可 RED | 多数可先写断言脚本再实现配置。但 **inhibit 类（AC-US5）是时序敏感集成测试**：需 NotReady(for 5m) + CrashLoop(for 10m) 同时 firing 再查 AM API inhibited 状态，"红"可能源于"告警还没 fire 满"而非"没配 inhibit"，红绿语义模糊——此类标注为"集成测试、非确定红绿"，不强求严格 RED-first。 |
| **L2 MTTD 测量**（AC-NFR-01 北极星） | ❌ 不适用 RED | MTTD 是测量值（中位时间 + 送达率），不是 pass/fail 断言，无红绿态。改为"**骨架先建（Phase C）、基线后测（Phase F 全量演练取中位）**"。 |

> **v0.3 补充**：RED-first 只服务于**闭环②（agent 预演）**，保证 agent 先把验收门/断言写出来再去实现。**闭环⑤（用户复现）**是照手册操作、不涉及 RED——用户手动跑的是手册里的命令和验收断言，不是写测试。
>
> **v0.6 补充（M4）**：操作手册是**闭环③预演收尾的独立产物，不占 plan task**——plan 保持纯部署 TDD 格式（避免 writing-plans 因"最后 task 是非 TDD 文档"而格式不合法）。手册产出由提示词③强制（plan 所有 task 完成后作为收尾步骤产出草稿）。

**故障注入脚本复用**：Phase A 写的 `inject-fault.sh`（预留 NotReady / CrashLoop / OOM / PodPending / 控制面接口）会被 C（MTTD 测量）、D（自监控验证）、F（全量演练）复用——Phase A 的 plan 里就要把注入接口设计成可扩展的，避免后续返工。这个脚本也是手册"验收"章节的核心工具，用户复现时直接用它注入故障。

#### 7.1.1 关键 OQ 的 MVP 处理策略（v0.5 已决）

阻塞型 OQ 不闭环就无法开工，以下为 MVP 阶段处理策略（生产割接前替换真实值即闭环 OQ 本身）：

| OQ | MVP 处理策略 |
|---|---|
| **OQ-3** 值班人 | **配置驱动 + 占位值**：namespace→owner / severity→@谁 做成 K8s Secret/ConfigMap（不硬编码进模板），MVP 填占位值（如维护者自己钉钉号），验路由 + @字段渲染 + 模板对；生产前换真实值班清单。**衔接（v0.6）**：Phase B 首 task 建 oncall ConfigMap，Phase C 只读不改（修复 M2） |

| **OQ-6** 钉钉两群 | **分阶段建群**：Phase C 只建主告警群 1 个机器人（全程真测试群），但 webhook-dingtalk 的 AM route tree **一次配齐 main + watchdog 两个 receiver**（watchdog receiver 在 Phase D 才挂真实群，receiver 定义提前到位，避免 D 第三次改 AM config，修复 M2）；监控健康独立群 Phase D 建 |

### 7.2 设计取舍（v0.5 已决）

1. ✅ **alertmanager 临时偏离 06 基线**：**Phase A 开单副本**（快速看第一条告警），Phase B 首 task 升回 3 副本（硬回收点）。接受受控临时偏离，换早期反馈速度。
2. ✅ **Phase C 钉钉**：**全程真测试群**（不用 mock）。前提：Phase C 预演前维护者建一个钉钉测试群 + 自定义机器人，webhook + 加签 secret 入 K8s Secret 不入 Git。agent 预演就用真群，踩加签/限流/截断坑写进手册。
3. ✅ **6 阶段切分**：**认可，无微调**（D+E 不合并、Phase A 规则裁剪暂不预拆 A.5；若某 plan 超 ~400 行再按 §3.2 提示拆）。
4. ✅ **用户复现的边界**：**agent 只答疑不代跑**。用户照手册自己操作（复制粘贴 OK），卡住时 agent 用 `systematic-debugging` 帮 root-cause 但不代敲/代改。默认模式；时间紧可临时降级为"卡住处可代跑"。
