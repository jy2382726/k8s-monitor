# Phase C · 钉钉触达 实现计划

> **For agentic workers:** REQUIRED SUB-SKILL: 用 `superpowers:subagent-driven-development`（推荐）或 `superpowers:executing-plans` 逐 task 执行本计划。步骤用 checkbox（`- [ ]`）跟踪。

**Goal（目标）**：建 `prometheus-webhook-dingtalk`，接通 Phase B 留下的 4 个 receiver 管道，把告警**真实送达钉钉**——主告警群收到**自包含富 Markdown**（含可执行 kubectl + 责任人 @手机号 + Runbook 公网链接字段）+ 监控健康群接通 Watchdog 心跳 connector（早验，formal 留 Phase D）+ **MTTD 测量骨架**单次打通。**验收门 = 链路送达**（真实到达钉钉群 + 字段齐全 + @人 + MTTD 单次可测）。

**Architecture（架构）**：
- **raw k8s manifest 部署**（非 helm）：`helm search repo dingtalk` 全 repo `No results`——prometheus-webhook-dingtalk 的 helm chart **已不在任何活跃 repo**（项目长期停更，原 prometheus-community chart 已移除）。故用 raw manifest（Deployment + Service + ConfigMap + Secret），符合本仓库「IaC / k8s YAML」形态，**不算重开选型**（组件仍是 06 锁定的 prometheus-webhook-dingtalk，只是部署载体从 helm chart 改 raw manifest，因 chart 客观不存在）。
- **富 Markdown 降级**（⚠️ 关键决策，见下方声明）：prometheus-webhook-dingtalk **v2.1.0 的 `Build()` 硬编码 `MessageType:"markdown"`**（`notifier/notification.go`，代码路径从不生成 actionCard；模型虽有 `DingTalkNotificationActionCard` 字段但未使用，配置/示例全是 markdown）。即**这个组件发不出真 ActionCard**。Phase C 用富 Markdown 实现「自包含 P0/P1 告警」——满足 AC-US3 自包含契约（kubectl + 公网 Runbook + @人，不依赖 VPN），区别仅是无按钮。PRD §8.2/L212 本就把 ActionCard 单按钮列为 Could 级（C1-C2）。真 ActionCard 形态（需 fork 改源码）记为待决 OQ。
- **不改 AM config（零修改型）**：Phase B 的 `alertmanager.config` 已把 4 个 receiver 的 webhook URL 指向 `prometheus-webhook-dingtalk.monitoring.svc:8060/dingtalk/<target>/send`（实测 decode generated secret 逐字一致，见前置状态）。Phase C 只需**建一个 Service `prometheus-webhook-dingtalk:8060`** + 配 4 个 target，URL 即可达——**AM config 一行不改**（design ⑧c「main+watchdog receiver 在 B 已配齐，C 只挂真实 endpoint，避免第三次改 AM config」）。
- **connector path 契约**：webhook-dingtalk HTTP path = `/dingtalk/<target-name>/send`（zread API Reference 实测）。故 4 个 target 名必须**精确等于** AM receiver URL 的第二段：`dingtalk-default` / `dingtalk-markdown` / `dingtalk-actioncard` / `watchdog-health`。
- **凭据组装（引用名不写值）**：4 个 target 的 `url`（含 access_token）+ `secret`（加签）+ `mention.mobiles`（手机号）需真实值，但 webhook-dingtalk **不支持 env 插值 config**。方案：assemble 脚本（**入 Git**）从闭环⓪已就绪的 `dingtalk-credentials-main`/`dingtalk-credentials-watchdog` Secret + `oncall` ConfigMap **读值**（只引用名）→ `envsubst` 骨架 → 生成 `webhook-dingtalk-config` Secret（**凭据型，不入 Git**）。自包含模板（Go template，非敏感）入 Git 的 ConfigMap。
- **加签 / @人由 webhook-dingtalk 自动处理**：config target 配 `secret` → webhook-dingtalk `SendNotification` 自动算 `timestamp(毫秒)+"\n"+secret` → HmacSHA256 → base64 → URL append `&timestamp=&sign=`（PRD L301 算法，`notifier/notification.go` 实测）；config target 配 `mention.mobiles` → `Build()` 自动映射钉钉 `at.atMobiles` + 文本追加 `@手机号`，默认模板 `default.tmpl` 已含 `{{ range .AtMobiles }}@{{ . }}{{ end }}`。
- **TDD 适配**（`docs/14` §5）：**L0** verify-all 检查 RED-first（Task 1 先写 dingtalk-check.sh 必 FAIL→部署→PASS）；**L1** 行为契约先写断言再实现（Task 3 写链路送达断言→实现/调模板→GREEN，但「查钉钉群」非确定 API 断言，红绿半模糊——脚本查 webhook-dingtalk 日志 `errcode=0` + 自指标 delta 确定性证明「发出且钉钉接受」，群里看到卡片 + 字段齐全由人工确认，design ⑥）；**L2** MTTD 骨架先建、不适用 RED（单次测量值，非 pass/fail）。

**Tech Stack**：prometheus-webhook-dingtalk **v2.1.0**（DockerHub `timonwong/prometheus-webhook-dingtalk:v2.1.0`，VERSION 文件 = 2.1.0；预演时 `docker pull` 确认 tag 实为 `v2.1.0`，若 not found 试 `2.1.0`）/ raw k8s manifest（Deployment + Service + ConfigMap + Secret）/ Go template（webhook-dingtalk 模板引擎，复用 AM 同款 `{{ }}` 语法 + sprig 函数）/ bash + AM `/api/v2/alerts` API + webhook-dingtalk `/metrics` + pod 日志。kubectl context = `kind-k8s-monitor-dev`。

**上游输入**：`docs/superpowers/specs/2026-07-10-phase-breakdown-design.md` Phase C 段（①–⑧） · `docs/14` §3.3 双轨闭环 / §5 IaC-TDD L0/L1/L2 / §7.1.1 OQ-5/6 MVP 策略 · `specs/prd.md` §6.3 F-SelfContained（自包含字段 + 加签算法 L301）/ §6.4 F-Severity（severity→P0-P3→@策略表）/ §11.1 北极星 MTTD / AC-US1-01 / AC-US3-01 / AC-NFR-01 · `specs/research/06` §3.4（路由树，B 已落地）/ §3.6.2（自包含策略）/ §3.10.2（Watchdog 独立群）/ §3.12.5（升级策略 @人）。

## ⚠️ 关键决策声明（写 plan 前已与维护者确认）

1. **富 Markdown 降级**：webhook-dingtalk v2.1.0 `Build()` 硬编码 markdown（实测 `notifier/notification.go`），发不出真 ActionCard。Phase C P0/P1 用富 Markdown（自包含 kubectl + @人 + Runbook 字段）。**真 ActionCard 形态（需 fork 改源码）= 待决 OQ**（违反「不重开选型 + 无应用代码」Non-Goals，故不在 Phase C 做）。design 验收门「ActionCard 真实到达」重新解读为「**自包含告警真实到达钉钉主告警群 + 含可执行 kubectl + 责任人 @手机号 + Runbook 链接字段在位**」——消息形态从 ActionCard 降级富 Markdown，自包含契约（AC-US3 核心）不变。
2. **raw manifest 部署**：chart 不存在（`helm search repo dingtalk` = No results），用 Deployment + Service + ConfigMap + Secret。
3. **OQ-6 取舍 = ②（接通 watchdog connector）**：watchdog Secret 已就绪，Phase C 顺手接通 `watchdog-health` target 早验 Watchdog 心跳链路（合成 Watchdog 告警 → 监控健康群）。**Watchdog 独立群 formal 验收仍属 Phase D**（Watchdog 正式规则 1h 心跳在 D 才上，C 只验 connector 链路通）。
4. **不改 AM config（零修改型）**：Phase B 已配齐 receiver URL，Phase C 建服务即通，AM config 一行不动 → teardown 修改型 = 无（最干净）。

- [ ] **Step 3: 写 verify-all 的 RED 检查器 dingtalk-check.sh**

Create `deploy/verify/dingtalk-check.sh`:
```bash
#!/usr/bin/env bash
# deploy/verify/dingtalk-check.sh
# Phase C webhook-dingtalk 检查（verify-all 调用）：Deployment 1 Ready + Service port 8060 + webhook 进程健康。
# 退出 0=OK，非 0=FAIL（打印原因）。
set -uo pipefail
ready=$(kubectl -n monitoring get deploy prometheus-webhook-dingtalk \
  -o jsonpath='{.status.readyReplicas}' 2>/dev/null)
[ "$ready" = "1" ] || { echo "webhook-dingtalk readyReplicas='$ready'（期望 1）"; exit 1; }
port=$(kubectl -n monitoring get svc prometheus-webhook-dingtalk \
  -o jsonpath='{.spec.ports[0].port}' 2>/dev/null)
[ "$port" = "8060" ] || { echo "Service port='$port'（期望 8060，对齐 AM receiver URL :8060）"; exit 1; }
# webhook 进程健康（prometheus common /-/healthy）
kubectl -n monitoring port-forward svc/prometheus-webhook-dingtalk 18060:8060 &>/dev/null & PF=$!
sleep 2
code=$(curl -s -o /dev/null -w "%{http_code}" --max-time 5 http://localhost:18060/-/healthy 2>/dev/null)
kill $PF 2>/dev/null
[ "$code" = "200" ] || { echo "webhook /-/healthy HTTP=$code（期望 200）"; exit 1; }
echo "webhook-dingtalk OK：1 Ready + Service:8060 + /-/healthy 200"
```

赋权 + 语法自检：
```bash

bash -n deploy/verify/dingtalk-check.sh && echo "✓ 语法 OK"
```

> **L2 不适用 RED**（docs/14 §5）：MTTD 是测量值（中位时间 + 送达率），非 pass/fail。Phase C 只**打通单次测量链路**（design ⑦降级 + PRD §11.1 北极星）。机制：

```bash
# deploy/verify/measure-mttd.sh
# Phase C MTTD 测量骨架（L2，单次，非 pass/fail）。
# T0 = inject-fault.sh T0_LOG 末行 epoch 秒（OQ-5）；T_detect = webhook-dingtalk 发送时刻（近似卡片到达）。
# MTTD = T_detect - T0。统计达标（N 样本中位）留 Phase F。
#
# 用法：./deploy/verify/measure-mttd.sh [alertname]    （默认取 T0_LOG 末行 type 对应 alertname）
#   典型：先 ./deploy/verify/inject-fault.sh not-ready k8s-monitor-dev-worker
#         再 ./deploy/verify/measure-mttd.sh KubeWorkerNodeNotReady

set -uo pipefail
NS=monitoring
T0_LOG="${T0_LOG:-/tmp/inject-fault-T0.log}"
ALERT="${1:-}"

G=$'\033[1;32m'; C=$'\033[1;36m'; Y=$'\033[1;33m'; N0=$'\033[0m'
info(){ printf "${C}▶ %s${N0}\n" "$*"; }

info "[1/3] 读 T0（inject-fault.sh T0_LOG 末行）"
[ -f "$T0_LOG" ] || { echo "✗ T0_LOG 不存在（$T0_LOG）。先跑 inject-fault.sh <type>。"; exit 2; }
last=$(tail -1 "$T0_LOG")
t0_type=$(echo "$last" | awk '{print $1}')
t0=$(echo "$last" | awk '{print $2}')
t0_human=$(echo "$last" | awk '{$1=$2="";print substr($0,3)}')
info "  T0: type=$t0_type epoch=$t0 ($t0_human)"
[ -n "$t0" ] && [[ "$t0" =~ ^[0-9]+$ ]] || { echo "✗ T0_LOG 末行格式异常：$last"; exit 2; }
# alertname 默认映射（按 type）
[ -n "$ALERT" ] || case "$t0_type" in
  not-ready) ALERT="KubeWorkerNodeNotReady" ;;
  crashloop) ALERT="KubePodCrashLooping" ;;
  oom) ALERT="KubeContainerOOMKilled" ;;
  pod-pending) ALERT="KubePodPending" ;;
  *) ALERT="$t0_type" ;;
esac
info "  目标 alertname=$ALERT"

info "[2/3] 读 T_detect（webhook-dingtalk 日志里发送 $ALERT 的时刻）"
# webhook-dingtalk 日志时间戳格式预演实测；用 log first occurrence 时间近似 webhook 发送时刻
wd_ts=$(kubectl -n "$NS" logs deploy/prometheus-webhook-dingtalk --tail=200 2>/dev/null \
  | grep -i "$ALERT" | head -1 | awk '{print $1}')
# 尝试解析日志首字段为时间（klog 格式 MMDD HH:MM:SS.ffffff 或 RFC3339）。预演实测日志时间格式后校正解析。

if [ -z "$t_detect" ]; then
  printf "${Y}⚠ 无法从 webhook 日志解析 T_detect（日志格式: '%s'）${N0}\n" "$wd_ts"
  echo "  预演校正：用 'kubectl logs --timestamps' 或 klog 格式解析。或手动记 webhook 发送时刻。"
  echo "  fallback：本次只验 T0 可读（T_detect 解析留预演），MTTD 测量链路骨架已建。"
  exit 0
fi

info "[3/3] 算 MTTD（单次，非统计）"
mttd=$((t_detect - t0))
printf "${G}MTTD（单次, $ALERT）= ${mttd}s ≈ $((mttd/60))m$((mttd%60))s${N0}\n"
printf "${Y}⚠ 含规则 for 防抖（产品有意设计）。额外开销 = MTTD - for 时限，应 ≤ 60s（PRD §11.1）。${N0}\n"
printf "${Y}⚠ T_detect 用 webhook 发送时刻近似（webhook→钉钉 <10s）。统计中位留 Phase F。${N0}\n"
```
