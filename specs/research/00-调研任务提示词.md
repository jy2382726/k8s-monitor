# 调研任务：K8s 集群监控系统 · 产品立项调研

## 项目定位

面向中型 K8s 集群（10-100 节点，1-3 集群）的运维监控系统。
目标：实时检测节点状态异常（NotReady/重启）、Pod 异常（OOMKilled/
CrashLoop）、资源水位（CPU/内存/磁盘）、网络异常，并通过钉钉、
邮件、短信多渠道通知对应运维人员。

所有文件写入 `specs/research/`：
- `specs/research/01-产品形态.md`
- `specs/research/02-API服务.md`

- `specs/research/04-实现方案.md`
- `specs/research/05-决策汇总.md`（由主 Claude 串行完成，最后写）

## 调研主题 4：实现方案

**由 sub-agent 4 独立完成，写入 `specs/research/04-实现方案.md`**

把系统拆成以下 6 个模块，每个模块给业内主流方案 + 推荐：

| 模块 | 调研维度 |
|------|---------|
| 数据采集层 | node-exporter vs 自研 agent；kube-state-metrics 部署模式；K8s API Watch vs Pull 轮询；网络探测（blackbox-exporter ICMP） |
| 指标存储层 | Prometheus 本地存储 vs VictoriaMetrics；100 节点集群每日数据量估算；数据保留策略；多集群统一存储（Thanos / Cortex / Victoria Cluster） |
| 告警规则引擎 | Prometheus 原生 AlertingRule vs 外部引擎；CrashLoopBackOff 标准 PromQL 规则；动态阈值 vs 静态阈值；告警抑制/分组最佳实践 |
| 通知网关 | Alertmanager 原生 vs PrometheusAlert（feiyu563）vs 自研；按 namespace/服务责任人路由告警的实现方案；告警收敛（同类 N 分钟合并）实现方式 |
| 多集群管理 | 每集群独立 Prometheus vs 中心化采集；跨集群统一视图方案（Thanos Query / VM Federation） |
| 运维大盘 | Grafana K8s 标准 Dashboard（kubernetes-mixin 等）；告警配置界面是否需要自建；部署方案（Helm / Operator）|

每个模块产出：
- 业内主流 2-3 个方案 + 各自优劣
- 推荐用什么 + 理由（要写"为什么不用 X"）
- 大致工作量预估（人天）

产出：`04-实现方案.md` —— 方案对比 + 推荐技术栈 +
      架构图（Mermaid，含完整数据流：采集→存储→告警→通知）
